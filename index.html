WebRTC for the Streamer

We wrote this site to share and explain the ways that we believe WebRTC (WHIP/WHEP) can improve streaming.

Many features of WebRTC are available in other protocols, such as SRT, MoQ, or RIST, but the protocol itself isn't the important part. We would just like streamers to know what is possible. These improvements can change so many things around streaming for the better.

WebRTC for the Streamer was written by the developers who added WHIP/WebRTC support to OBS and maintain Broadcast Box. A companion piece to this site is WebRTC for the Curious.

Streaming can be better... Try it Now!

Speed

WebRTC has ~200ms latency. Interact with your viewers and friends like a video call! Everything is more connected and fun.

Privacy

WebRTC has End-to-End Encryption (E2E). When enabled, servers can't watch or tamper with your stream. Only your viewers can decrypt it.

Everyone Streams

WebRTC lets you stream from a web browser directly, no download necessary. Convince a friend to stream for the first time or bring entirely new types of people into streaming that couldn't do it before!

Higher Quality

WebRTC supports the latest audio and video codecs including AV1, which can deliver about 30% better quality at the same bitrate.

Self Hosted

WebRTC uses one protocol for publishing and playback. Since WebRTC is widely used outside of streaming, lots of open source servers already exist.

Stream Anywhere

WebRTC adapts to ever-changing network conditions. Try streaming on cellular, satellite, or bad Wi-Fi!

Speed

With WebRTC you get sub-500ms latency you'll have the experience of a video call. Most streaming platforms today have >2000ms latency, even if there's "no lag".

Streaming to friends

Streaming to your friends feels more lively when the latency is lower. Have fun recreating the "sitting on the couch together" experience when you stream games or movies with friends!

Co-streaming to an audience

When co-streaming to an audience you want the lowest latency possible. It allows you to have authentic conversations with the other streamer, instead of an awkward back and forth. When streaming games, higher latency can cause streams to desync between you and your partner's gameplay. This can lead to a confusing viewer experience if events happen at different times on each stream.

Audience interaction

WebRTC allows you to respond to chat like... a chat! It feels like a real conversation when you can talk to chat instantly, instead of reading their reactions multiple seconds after something cool. The audience interaction isn't limited to only text! Some games allow the audience to change the game environment itself. Seeing games instantly react when sending a message as a chatter is a magical experience!

Privacy

WebRTC provides APIs that lets streamers encrypt media and viewers decrypt it so the server has no access to the video. The server can support all different types of clients thanks to simulcast.

Self Hosted

WebRTC has quite a few self-hosting options. This has happened for a few reasons.

Wide usage outside of streaming

WebRTC is widely used outside of streaming. It's used for robotics, conferencing, "AI voice assistants" and more. It can benefit from the ecosystem that existed before WebRTC streaming.

One protocol for publish and playback

If you are using RTMP you have to use another protocol for playback (usually HLS or DASH). With WHIP and WHEP you can use WebRTC for both, which means fewer moving parts to run.

Cheaper to run/no transcoding

A WebRTC server just forwards media packets instead of transcoding the stream. It's a lot easier to deploy, manage, and scale.

Simulcast

When streaming video you will need to support different types of users. A phone on 5G works best with 1080p while a desktop computer with fiber can support 2160p (4k). Simulcast makes the streamer generate and upload all quality levels so the server can forwards the different video feeds to the appropriate viewers.

Traditionally with streaming software you would upload the 2160p feed, and the server would transcode down to the other layers (2160 -> 1440, 1080, 720, etc.). WebRTC's approach to this problem has a few benefits.

Better quality

A 1080p video stream generated via transcoding will not have the same quality as one generated in OBS directly. Transcoding suffers from generational loss: a video that is decoded and re-encoded will have additional compression artifacts and loss of detail. With simulcast you only encode once.

More control

A transcoding approach means you can only control the encoding quality of the highest quality stream, whereas simulcast lets you set all your video streams to be high quality.

Lower latency

Transcoding adds latency since it has to run an additional decode + encode. Your transcoded feeds will have a different latency compared to your uploaded feed. With simulcast, all your feeds run at the same latency.

Simpler servers

Running servers without transcoding is much easier. Transcoding requires a lot of computing power to crunch video data, while simulcast just handles a little more upload traffic.

No tampering/ad insertion

Simulcast means you pass through video feeds untampered. If the server is re-encoding your stream it reduce the quality, or potentially insert watermarks/ads or mess with your stream in unexpected ways. With E2E encryption, streamers can make it so the server itself can't even decode your video. The server will only see a stream of bytes pass through, but it can't decrypt the video.

Everyone Streams

Streaming from the browser increases accessibility. The video quality won't be as good (compared to using broadcasting software directly), but every voice matters.

Everyone can stream

Today, streaming means you have to install dedicated software. Configuring software means you have to be aware of things like bitrate, codecs, and your resource usage. Streaming from a browser significantly reduces the barrier of entry to streaming. So many new voices and types of streams will be available when it is opened to more people!

Browser is everywhere

A web browser is available everywhere. You can find them on phones, TVs, tablets, cars, and refrigerators! People can stream from so many places where it wasn't available before. Anyone using computers that can't install additional software can now stream without having to request installation privileges on the machine.

Stream Anywhere

WebRTC gives a lot of flexibility in how you can stream. You can configure it to have the lowest latency possible (at the expense of video quality) or you can run it over TCP and have perfect video quality but higher latency. These are just a glimpse of the knobs that WebRTC gives you!

Protocol choice (TCP or UDP)

WebRTC allows you to choose, per session, if you want TCP or UDP. If you pick TCP you will have zero packet loss, but may experience higher delay. If you pick UDP you get more control over the experience. You can use things like FEC+NACK to accommodate for a poor network while keeping your latency as low as possible possible.

Sender driven bandwidth estimation

WebRTC lets a streamer dynamically change their bitrate if needed. WebRTC has a mechanism built into the protocol that constantly measures packet loss and delivery time RFC 8888. Instead of setting a static bitrate, you can dynamically change your bitrate to get the best experience possible for your network/hardware.

Below is a simplified example. Streaming software starts at 1080p and tries to upgrade to 2160p. If that results in a bad experience it drops back to 1080p. WebRTC provides the receiver feedback needed to make these decisions. 

            sequenceDiagram
                OBS->>Server: Sending 1080p
                Server-->>OBS: Zero Packet Loss, 50ms trip time
                OBS->>Server: Sending 2160p
                Server-->>OBS: Packet Loss, 150ms trip time
                OBS->>Server: Sending 1080p
                Server-->>OBS: Zero Packet Loss, 50ms trip time

Forward error correction (FEC)

Forward error correction allows you to send redundant/duplicated info in advance so packet loss has no impact on the stream. It consumes extra bandwidth, but is a great solution if you are streaming over satellite/cellular and have bandwidth available but are combating packet loss.

Negative-acknowledgement (NACK)

NACK is another error correction technique. Instead of the streamer sending duplicate data in advance, the receiver asks for any missing packets. This is a good fit when packet loss is small and the stream still has time to repair the frame. It uses less bandwidth than FEC, but if the network is too delayed then the resent packet might arrive too late to be useful. 

            sequenceDiagram
                participant OBS
                participant Server
                OBS->>Server: Sending packet 101
                Note over OBS,Server: Packet 102 is lost
                OBS->>Server: Sending packet 103
                Server-->>OBS: NACK packet 102
                OBS->>Server: Re-send packet 102
                Server->>Server: Build video frame from 101, 102, 103

Mobility (ICE renomination)

Switching between WiFi/cellular used to require a full reconnect of the stream. With WebRTC you can switch networks without disconnecting anything. The network switch also allows for easier administration. Servers can be updated or restarted without requiring users to fully disconnect from the stream.

Connection bonding

WebRTC allows accepting video from multiple sources. You can combine multiple 5G/WiFi interfaces and send video over them. This technique is niche, but it opens up lots of interesting options. You can send your most important video feed over your most stable interface. Some users will also send their more latency sensitive media (audio) over one interface while using others for video.

Higher Quality

WebRTC does not hardcode video codecs into the protocol. Codecs are negotiated at runtime so other codecs (like HEVC and AV1) can be trivially added. AV1 is designed to deliver about 30% better quality at the same bitrate, so a 6 Mbps stream can look noticeably better without requiring more upload bandwidth. Custom codecs could also be added if both client/server supported so you can do custom things if you need.

How can I use WHIP/WHEP?

Clients

  • OBS Studio - desktop WHIP publishing.
  • FFmpeg - command-line WHIP publishing with the WHIP muxer.
  • GStreamer whipclientsink - pipeline-based WHIP publishing.
  • GStreamer whepclientsrc - pipeline-based WHEP playback.
  • Larix Broadcaster - mobile WHIP publishing from iOS and Android.
  • Eyevinn WHIP web client - browser-based WHIP publishing SDK.
  • whip-go - Go WHIP client and command-line publisher.
  • VDO.Ninja WHIP/WHEP tool - browser WHIP publishing and WHEP playback.
  • Meetecho Simple WHIP Client - native GStreamer-based WHIP test client.
  • Meetecho Simple WHEP Client - native GStreamer-based WHEP test client.

Servers

  • Broadcast Box - simple WHIP ingest and WHEP playback for self-hosted broadcasts.
  • MediaMTX - live media router with WHIP publishing and WHEP playback.
  • OvenMediaEngine - streaming server with WebRTC/WHIP ingest.
  • SRS - real-time media server with WHIP and WHEP HTTP APIs.
  • LiveKit Ingress - WHIP and RTMP ingress service for publishing into LiveKit rooms.
  • Janus Simple WHIP Server - WHIP server library backed by Janus.
  • Eyevinn WHIP - WHIP endpoint and browser client modules.

Services with WHIP support

  • Dolby.io / OptiView Real-time Streaming
  • Red5
